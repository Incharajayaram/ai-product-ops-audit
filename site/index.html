OAuth2 dominates, but it's rarely alone. 76 of 100 apps support OAuth2 — but 56 also offer a plain token and 42 offer a static API key for the single-workspace case. The practical reading: don't build an OAuth-only toolkit. Most vendors expect small integrations to skip OAuth entirely and use a key, reserving OAuth for multi-tenant marketplace apps.

Self-serve is the default, not the exception. 65% of apps let a developer get working credentials for free, immediately, with no conversation. Only 20% require either a paid plan or manual approval before you can even get a key.

Where gating does happen, it's category-shaped. Productivity & Project Management is 10-for-10 self-serve — these vendors treat free API access as a growth lever. Support & Helpdesk is the most gated category: Zendesk, Pylon, Help Scout, Gorgias and Aircall all put API access behind a paid seat, because for a helpdesk vendor the API itself is a premium feature, not a developer-relations line item.

The quietest pattern: 13 apps whose docs are fine technically and silent commercially. Their authentication pages explain token types in detail but never say whether getting one costs money. That's not a blocker — it's unpaid research time: someone has to actually sign up to find out.

* has_existing_mcp counts any MCP server surfaced in search results, official or third-party. Verification caught at least one case (Zendesk) where this overcounted — see Verification.

# App Category Access Buildable MCP

The agent that did this

Not a demo wrapper around search — a pipeline, built on Composio's own SDK, that ran unattended across all 100 apps.

1

A Composio session, scoped to one toolkit

A single Tavily connected account (composio.connected_accounts.initiate) wired into a Composio session via the Python SDK (composio.create(toolkits=["tavily"])). Every search and page-extract call for every app goes through Composio's session, not a raw Tavily client — that's the "build it with Composio" part, not just the research.

2

Two searches + two page extracts per app

One broad discovery search ("API documentation authentication"), one commercial-access search ("sign up, pricing, approval, MCP"), both anchored to the app's known domain to avoid name collisions. The top two ranked URLs get a full-page extract; everything else stays as a search snippet.

3

Structured extraction, not free text

Gemini turns the evidence block into a typed record (Pydantic schema: auth methods, self-serve status, API surface, MCP status, buildability verdict, evidence URLs, a self-reported confidence score) — told explicitly not to guess, and to say "unknown" rather than assume a common default.

4

Concurrent, resumable, logged

4 workers in parallel, each app's result flushed to a JSONL file immediately, so a crash loses at most one in-flight app, not the run. 100/100 apps completed after two operational fixes below.

Where it needed a human

Caught in the first smoke test

"Sherlock" meant the wrong product

The assignment's "Sherlock" is the OSINT username-search CLI (github.com/sherlock-project/sherlock). An unqualified search for "Sherlock API" instead surfaced an unrelated AI platform of the same name, and the agent confidently wrote up that product's auth model. Fixed by anchoring every query to the app's known domain and telling the model explicitly to check sources against the hint before using them — this is now a standing guard, not a one-off patch.

A real infrastructure wall, not a code bug

Gemini 2.5 Flash's free tier allows 20 requests a day

The first full run died silently after 8 apps with a quota error I hadn't budgeted for — the model's free tier caps at 20 requests per day, not per minute. Switched to gemini-3.5-flash-lite (a per-minute limit, which ordinary retry/backoff handles), and the remaining 92 apps completed in one run.

Found auditing my own verification code

My first verification pass produced corrections I couldn't use

Early "corrected" values came back as free text — "freemium", "available" — that didn't match the schema's actual enum values, so they could be logged but not safely applied to the dataset. Rewrote the verifier's output as the same typed enums as pass one, which is also what pushed the usable field-accuracy reading from an unreliable 63.5% to a clean 93% on claims the evidence actually addressed.

Verification: two independent loops

Sampling, not spot-checking: 13 lowest-confidence apps plus one random app per category (23 total, weighted toward where errors are likely but still checking for false confidence elsewhere).

Loop 1: an independent agent re-check

For each sampled app, a second, differently-worded, independently-gathered search — then Gemini judges pass-1's claims against that fresh evidence only, field by field, required to answer with the same validated enum, never a guess.

Loop 2: a human actually reading the pages

I opened the real source pages for 3 apps by hand. One came back clean, one showed the automated loop catching a real miss, and one showed the automated loop missing something a closer read caught — which is the point of keeping a human loop at all.

Known limitations

  • MCP status is a first-pass signal, not a confirmed fact. has_existing_mcp doesn't reliably distinguish an official vendor MCP server from a third-party wrapper, or from a feature that consumes MCP rather than exposing one (Zendesk ships an MCP client for its own workflow builder, not an MCP server for outside agents — both pass 1 and the automated verifier missed that distinction; only the human check caught it).
  • 13 "unknown" self-serve verdicts are an honest gap, not a dead end. They mean the public docs don't state commercial terms — resolving them needs an actual signup attempt, not another search.
  • One search pass per app, not a deep dive. The agent gives each app roughly the attention a developer would spend before deciding whether to keep investigating — real ambiguous cases (shared product names, multi-product companies) need the kind of targeted, hint-anchored follow-up query this pipeline only applies on the verification sample, not on every app automatically.
  • Verified-correct still means "correct against the evidence gathered," not against ground truth no search surfaced. A 93% field-accuracy figure describes agreement with a second independent search, which is the strongest check available without manually opening all 100 apps' docs by hand.
